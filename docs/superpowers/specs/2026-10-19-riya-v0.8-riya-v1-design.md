# Riya v0.8: "Riya v1" (her own small model)

Design document. Date: 2026-10-19. Status: approved on autopilot (the user delegated decisions: "continue … until we make the full polished riya").

## 1. Intent

Riya's local brain is LFM2.5-1.2B, a general instruct model. The persona sheet, style examples, deterministic paths and
shaping already carry it a long way. The live persona scorecard still sits around 8/12, and it misses on four things:
- generic-assistant phrasing (about 23%, target ≤ 15%);
- occasional invented memories (target 0);
- unknown-fact honesty (about 75%, target 100%);
- about-me recall (about 67%, target ≥ 75%).

These are small-model habits that prompting can't fully fix. The roadmap's answer is "Riya v1": a LoRA fine-tune of
her local model on examples in her exact prompt format. A champion gate adopts it only when it measurably beats the
base model.

v0.8 builds the whole pipeline: dataset, filters, the Colab trainer, GGUF export, adapter loading, the champion gate
and the Health row. Running the training is the user's step, because it needs their Colab GPU. Everything up to the
"run this on Colab" line, and everything after the adapter file comes back, is automated and tested.

## 2. Goals
1. **Dataset builder** (`riya/train/build_sft.py`, run locally).
   - Training requests use the real `build_messages`: persona_local, style examples, a memory block, feelings, the
     reply-rules line, and the situation. Training therefore sees exactly the prompt shape she sees at run time.
   - Scenarios cover every live behaviour, each with known facts or none:
     - small talk;
     - about-me with facts, which must recall them and only them;
     - unknown facts ("do you remember my sister's name?" with no such fact), which must say she doesn't know;
     - identity; remember-that acknowledgements; explain;
     - greetings after short and long absences;
     - bids; game turns; tool result lines; feedback acks; agent reports.
   - Variety comes from a seeded generator: names, facts, moods, times of day, dial settings (v0.6) and notes.
   - Output: `requests.jsonl`, with one row per example: `{id, kind, messages, facts, expect}`. `expect` holds the
     checkable rules for that row: `must_mention` (facts), `must_not_invent`, `must_admit_unknown`, `max_sentences`,
     `max_emoji`.
2. **Teacher generation (Colab, user step).** Reuse the existing `colab/gen_riya_data.py` teacher pattern: llama-server
   running a larger uncensored instruct model with parallel slots. It reads `requests.jsonl` and writes
   `teacher.jsonl` (`{id, response}`). Optional fallback: the online model, rate-limited to the free tier. It is off by
   default.
3. **Filter** (`riya/train/filter_sft.py`, local and pure). Every teacher response is scored with the existing
   `style_metrics` plus the row's `expect` rules. A row is rejected if it:
   - uses a generic phrase;
   - goes over the sentence or emoji caps;
   - mentions a fact not in the memory block (invented memory);
   - misses a required fact;
   - doesn't admit an unknown;
   - has a disclaimer on a non-identity turn;
   - has a stage direction or a "Riya:" label.

   Output: `sft.jsonl` (chat format) plus a report of keep rates per kind. A kind with fewer than 40 kept rows is
   flagged.
4. **Trainer (Colab, user step).** `colab/train_riya_v1.py`:
   - PEFT LoRA on the HF LFM2.5-1.2B-Instruct base, r=16, alpha=32, dropout 0.05, targeting attention and MLP linears;
   - 2 epochs, lr 2e-4, cosine schedule, max length 2048;
   - loss on assistant tokens only;
   - fits a free T4 with 4-bit loading, falling back to bf16 on larger GPUs.

   It then converts the adapter to a GGUF LoRA with llama.cpp's `convert_lora_to_gguf.py` and writes
   `riya-v1-lora.gguf` plus `train_report.json` (loss curve and config) to Drive. A runbook,
   `colab/riya_v1/README.md`, gives the exact cells.
5. **Adapter loading.**
   - `riya/server.py` gains `--lora PATH` and passes it to llama-server's `--lora`, so the base GGUF is unchanged.
   - Settings get `local_adapter: str | None`, `None` by default. The start-up script passes the adapter when the
     setting is set and the file exists.
   - Game mode's CPU and GPU restarts keep the adapter.
6. **Champion gate** (`evaluation/champion.py`).
   - It runs `persona_eval --repeat 3` for the base and the candidate (base + adapter), on temp DBs, and pools the
     metrics.
   - **Adopt** when both hold:
     - the candidate meets at least as many targets as the base, and improves at least two of the four weak metrics
       by ≥ 10 points pooled;
     - no anti-goal metric regresses beyond noise (±5 points pooled): AI honesty, disclaimers, unknown honesty,
       invented memories (must not increase), and tone/rudeness flags (none).
   - **On adopt:** it writes `local_adapter` and prints the comparison table. **On reject:** it prints why and changes
     nothing.
   - A `--dry-run` mode prints the decision without writing anything.
   - It manages its own llama-server process (start, health wait, stop) and never leaves one running.
7. **Health row "Local brain"** shows "LFM2.5 base" or "Riya v1 (adapter <date>, champion +N targets)". There is a
   one-click "Use base model" (a plain click, local) and "Use Riya v1" when an adapted file exists. Switching restarts
   llama-server through the existing server wrapper.

## 3. Non-goals and anti-goals
- **Non-goals:**
  - full fine-tuning;
  - training on the user's real transcripts (privacy; a later opt-in idea);
  - RLHF or DPO;
  - voice or TTS fine-tuning;
  - changing the base model;
  - automatic retraining.
- **Anti-goals:**
  - The adapter is adopted without beating the base on the gate, or it regresses honesty or tone.
  - Any of the user's real data (memories, transcripts, notes, screen notes) goes into the dataset or to the teacher.
    The dataset is synthetic only, with seeded fake names and facts.
  - A broken or missing adapter file stops Riya from starting. Her fallback is the base model, with a warn Health row.
  - The gate leaves a llama-server running, or runs while the user is gaming. It refuses when presence is "gaming" or
    free VRAM is below 2.5 GB.

## 4. Design notes
- **Package `riya/train/`** holds pure, CPU-only code with no torch import:
  - `scenarios.py`: the seeded scenario generator, with fake people, facts and places;
  - `build_sft.py`: requests via the real prompt builder;
  - `filter_sft.py`: the scoring;
  - `fmt.py`: the chat-format rows the trainer reads, including the LFM2 chat template check.
- **Requests use the engine's own builders.** They are built by constructing the same inputs the engine would
  (`Retrieved` with fake facts, a feelings tag from a seeded `Feelings`, dials), so any future prompt change flows into
  training data automatically. A test asserts a request equals what `RiyaCore` would send for the same inputs.
- **Determinism.** `--seed`, `--n` (default 3000 requests) and `--kinds` select the mix. The same seed gives the same
  file.
- **The trainer stays in `colab/`.** It isn't imported by the core, and its logic is kept small: data loading, the PEFT
  config and the loop. CPU tests cover only its config builder and the assistant-only masking function, which work
  without a GPU on a tiny random tokenizer.
- **The champion gate reuses `persona_eval`'s run/score functions**, with a llama-server started per variant.
  Comparisons pool `--repeat` runs.
- **llama.cpp LoRA in GGUF.** llama-server supports `--lora <file>`, and `--lora-scaled` for strength. v0.8 uses
  scale 1.0.

### 4.1 Builder-check decisions (my calls, binding)
1. **Train on the weights she actually runs.**
   - The trainer's base is resolved in this order:
     1. The `BASE_ID` env var.
     2. An HF search for the safetensors repo of the GGUF she serves. Default:
        `huihui-ai/Huihui-LFM2.5-1.2B-Instruct-abliterated`, the abliterated weights matching her GGUF.
     3. The official `LiquidAI/LFM2.5-1.2B-Instruct`.
   - If it falls back to step 3, `train_report.json` records `"base_mismatch": true` and the runbook prints a loud
     warning. The champion gate is the final judge either way.
   - The converter's `--base` is the same resolved directory.
2. **Probes are held out.**
   - No `persona_eval` probe's user text appears in `requests.jsonl`. Text is normalised by casefold, collapsed
     whitespace and stripped punctuation, and checked for exact or substring matches of 6+ words.
   - The scenario templates are written independently of the probes.
   - A test asserts zero overlap.
3. **Per-metric "better" for the gate.**
   - A metric already at its target counts as *kept* if the candidate stays at the target, and *improved* if a
     not-at-target metric moves toward the target.
   - The noise band is computed from the pooled repeat variance: max(10 points, 2× the larger per-variant standard
     deviation).
   - Invented memories improve only if the count goes down. They must never increase.
   - **Adopt** when all of these hold:
     - the candidate meets at least as many targets as the base;
     - at least 2 of the 4 weak metrics improve beyond the noise band, or are already at target and kept;
     - nothing on the veto list regresses beyond the noise band.
   - The probe counts per metric are printed with the decision.
4. **LoRA targets.**
   - Attention `q_proj`, `k_proj`, `v_proj` and `out_proj`, plus the MLP `w1`, `w2` and `w3` only. The short-conv
     layers are excluded.
   - The Colab runbook runs a conversion smoke test before the full training run: one optimizer step, export, then
     `convert_lora_to_gguf.py`, then `llama-server --lora` load.
5. **Train in fp16 on a T4.** No 4-bit (bitsandbytes is not used).
6. **Server slots.** The slot-cache directory is keyed by adapter, so a cache saved under one variant is never restored
   under another.
7. **Paths and teacher.**
   - The adapter is copied to `C:/Users/sreev/models/riya/` (the user's model dir).
   - The teacher is the existing `colab/gen_riya_data.py` default (`TEACHER` env, Huihui-Qwen3.5-9B-abliterated).

## 5. Verification
- **Pure tests:**
  - scenario determinism and coverage of every kind;
  - request equals engine prompt (golden equality);
  - each filter rule, with keep and reject cases;
  - the expected fact-mention, invention and unknown-admission checks;
  - sft row format, plus the assistant-only mask on a toy tokenizer;
  - the champion decision table (adopt and reject cases, the noise bands, a regression veto);
  - server `--lora` argument passing, with the game-mode restart keeping it;
  - settings `local_adapter` validation;
  - a missing adapter falls back to base with a warn row.
- **Live, in-session:**
  - build a 3000-request dataset;
  - filter a tiny teacher sample produced by the local model as a stand-in teacher (format smoke test only);
  - `champion --dry-run` base-vs-base sanity, which must be "no change".
- **User steps (runbook):** run the teacher and the trainer on Colab, copy `riya-v1-lora.gguf` into `models/`, then
  run `python -m evaluation.champion`.
