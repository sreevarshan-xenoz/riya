# Riya v0.4: "Agent babysitting"

Design document · 2026-10-18 · status: approved (autopilot; decisions delegated by the user)

## 1. Intent

The user said: "while my agents work she can play with me and in bg she can monitor my agents". The v0.1 design adds
that she tells the user when something finishes, fails or needs their approval, in her own voice and mood. Failures
and approval requests break through even while the user is focused. A successful finish can wait until they look up.

The user's agents are **Claude Code sessions** (CLI on this Windows laptop) and **Colab training runs** (their existing
`colab/autopilot_watch.py` pipeline, with logs synced to `G:\My Drive\jarvis\runs`).

## 2. Goals
1. **Claude Code awareness through hooks.** Claude Code POSTs hook events to Riya (`http` hook type) at
   `http://127.0.0.1:8766/hook`, with a shared-secret header. Riya keeps a per-session state machine: busy, waiting
   (approval), idle or finished, failed, ended.
2. **Colab awareness through a log watcher.** A generic watcher polls configured log globs every 60 s for DONE, FAIL and
   LOST patterns (the same ones `autopilot_watch.py` uses), plus a staleness rule: no log growth for 30 min while
   "running" counts as stalled.
3. **Reporting with manners.**
   - **Needs approval or failed:** speaks one short line right away when the user is focused or talking, as a bubble
     only when gaming, and on return when away.
   - **Finished successfully:** queued, then delivered on the next break, the next talking turn, or the return greeting.
   - Every report has an expression: worried for failure, happy for finished, curious for approval.
4. **Agents area.** The body's panel shows the reserved agents area as a live list: name, status chip and age. Buddy mode
   shows a small badge with the count of agents needing attention. Window mode lists them under the chat.
5. **Keeping the user company while agents run.** When at least one agent is busy and the user is on a break or talking,
   her bids may offer a game. Three LLM-driven text and voice games: **word chain**, **20 questions** (she thinks of
   something) and **riddles**. Game state lives in the engine, and the user can say "stop" anytime.
6. **Easy, reversible setup.** `python -m riya.agents.install_hooks` prints the settings snippet and the token location.
   `--apply` merges the hooks into `%USERPROFILE%\.claude\settings.json` (after a timestamped backup), and `--remove`
   takes them out. Applying is a **user step**: it changes every Claude Code session on the machine.

## 3. Non-goals and anti-goals
- **Non-goals:**
  - Controlling agents (approving or denying from Riya). The user approves in Claude Code itself. Riya may say which
    command is waiting.
  - Parsing full transcripts.
  - Other agent frameworks; adapters can come later.
- **Anti-goals:**
  - A hook makes Claude Code slower or fail: always return 200 fast with an empty body, never a decision.
  - Riya speaks a payload's secret or long text: only summaries go out, truncated to 80 characters.
  - Unauthenticated local processes inject fake agent events: the shared secret is required.
  - A report while gaming that uses voice.

## 4. Design

### 4.1 Hook receiver (`riya/agents/hooks.py`)
- A second tiny FastAPI app inside the core process on `127.0.0.1:8766`. `POST /hook` requires the header
  `X-Riya-Token` to equal the token in `%LOCALAPPDATA%\Riya\hook_token`, which is created on first run with 32 random
  bytes in hex. It rejects a missing or wrong token (401) and any request carrying an `Origin` header (403). The body
  can be at most 256 KB.
- Handling: parse JSON, take `hook_event_name`, `session_id` and `cwd`, then dispatch into `AgentHub.on_claude_event`.
  Respond with 200 and an empty body within 50 ms; no work happens in the request path beyond enqueueing.
- The installer adds handlers for these events: `UserPromptSubmit`, `PermissionRequest`,
  `Notification(permission_prompt|idle_prompt)`, `Stop`, `StopFailure`, `PostToolUseFailure`, `SubagentStop`,
  `SessionStart`, `SessionEnd`. Each is `{"type": "http", "url": "http://127.0.0.1:8766/hook", "timeout": 3, "headers":
  {"X-Riya-Token": "$RIYA_HOOK_TOKEN"}, "allowedEnvVars": ["RIYA_HOOK_TOKEN"]}`. The installer also tells the user to
  set the `RIYA_HOOK_TOKEN` user environment variable, and offers `--apply` to set it with `setx`.

### 4.2 Agent hub (`riya/agents/hub.py`, pure state machine)
- An `AgentState` per id holds `kind` (claude or colab), `name`, `status`, `since`, `last_event_at`, `detail` and
  `needs_attention`.
  - For Claude, the name is the cwd's folder name plus a short session id.
  - For Colab, it's the watcher's name.
- Claude transitions:

  | Event | New status |
  |---|---|
  | UserPromptSubmit | busy |
  | PermissionRequest, or Notification:permission_prompt | waiting (`tool_name` and a short `tool_input` summary) |
  | Stop | finished (`last_assistant_message` truncated to 80 chars) |
  | StopFailure | failed (`error`) |
  | PostToolUseFailure | stays busy, adds `tool_error_count`; three in one turn counts as failed |
  | Notification:idle_prompt | idle |
  | SessionEnd | ended (removed after 10 min) |
  | SessionStart | idle |

  An agent that stays "busy" with no events for 30 min becomes `unknown`. That covers the Esc interrupt, which fires no
  Stop.
- Colab transitions come from the watcher: running, finished (DONE), failed (FAIL), lost (LOST) or stalled.
- Output is `AgentEvent(kind: finished | failed | waiting | lost | stalled, agent_id, text)` for the engine, plus a
  snapshot for the body.

### 4.3 Colab watcher (`riya/agents/logwatch.py`)
- Configured in settings as `agent_logs: [{name, glob, done_re, fail_re, lost_re}]`. The default has one entry for the
  user's setup: `G:/My Drive/jarvis/runs/**/*.out`. Its patterns come from `autopilot_watch.py`:
  - done: `STAGE0_TRAIN_DONE|ROLE_DONE|BENCH_DONE|GEN_DONE|TRAIN_DONE|PASS1_DONE`
  - fail: `FAILED|Traceback`
  - lost: `LOST`
- It polls every 60 s, reading only the bytes appended since the last poll (offsets persisted in KV). It never raises,
  and a missing path counts as "not configured".

### 4.4 Engine integration
- `AgentEvent`s go to a report queue. `tick()` delivers them per §2.3: urgent kinds are failed, waiting, lost and
  stalled; finished is calm.
- A report line is generated by the local model with a short situation ("Your agent in `riya` needs approval to run
  `npm test`."). The budget is 40 tokens, at most 1 sentence. The expression is set by kind.
- At most one spoken report every 20 s. Bursts are merged ("two agents finished").
- The prompt gets a `### Your agents:` line with active agents and their statuses, so she can answer "how's my agent
  doing?".
- Games:
  - `riya/core/games.py` holds the per-game system rules and state (turn count and the secret for 20 questions, stored
    in the engine and never in the prompt history the user sees).
  - It starts when the user accepts a game offer or makes a request at the start of a message ("let's play <game>",
    "can we play <game>", "how about <game>", a bare "<game>?"); a negated or passing mention never starts one.
  - It ends on "stop", a win or loss, or the game's length: 20 questions ends at 20 question-or-guess moves, and word
    chain and riddles end at 15 moves. Off-topic turns (chat mid-game) never count toward either. They get a normal
    reply with a "still mid-game" note, and the game stays on. A game also ends after 10 min with no turn.
    (Amended in the 5b fix round: the original "15 turns" made 20 questions a 15-question game.)
  - Game turns use the local model with game rules in the situation.

### 4.5 Protocol and body
- Core → body: `agents {items: [{id, kind, name, status, since, detail, needs_attention}]}`, sent on change and on
  hello.
- Body:
  - The panel's `#agents` area renders the list: status chip colours (busy, waiting, finished, failed, unknown), a
    relative age, and the detail on hover.
  - Buddy mode shows a corner badge with the needs-attention count.
  - Window mode shows a compact list above the chat log.
  - Clicking an item does nothing in v0.4 (a non-goal).
- Settings: an "Agents" section showing hook install status (received any event in the last 24 h: yes or no), the token
  file path, and the log-watch entries (editable).

## 5. Verification
- Pure state-machine tests per transition, with the staleness and merge rules.
- Receiver tests through TestClient: token required, Origin rejected, size limit, fast 200, and malformed JSON → 200
  with nothing enqueued.
- Logwatch tests on temp files: incremental reads, patterns, a stalled run, and offsets persisted across restarts.
- Installer tests on a temp settings file: merge preserves existing hooks, idempotent apply, remove restores, and a
  backup is written. It never touches the real file in tests.
- Engine tests: urgent report while focused, a finished report deferred to the break, nothing spoken while gaming,
  merged bursts, and the game lifecycle.
- A live check, `evaluation/agents_check.py`. It POSTs a scripted sequence of hook events to a running core with the
  token and prints the reports. It doesn't need Claude Code.
