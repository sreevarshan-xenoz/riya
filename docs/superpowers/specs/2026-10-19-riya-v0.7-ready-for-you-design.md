# Riya v0.7: "Ready for you"

Design document · 2026-10-19 · status: approved (autopilot; the user delegated decisions: "continue … until we make the full polished riya")

## 1. Intent

Riya v0.1–v0.6 is built, but several things only the user can do still live in terminal commands and README notes:
- putting a Gemini key in `.env`
- picking her voice with `python -m riya.voice_candidates`
- connecting Claude Code with `python -m riya.agents.install_hooks --apply`
- dropping in the art pack
- knowing whether her eyes and agents actually work

A polished companion should be ready to use from inside itself. v0.7 adds a first-run welcome in her voice and a Health page that shows what's set up and fixes what isn't. Every action that changes something outside Riya, or calls the network, happens only when the user clicks for it.

## 2. Goals
1. **First-run welcome.**
   - **When it opens.** The `onboarded` setting is false on a new install and true for existing users after migration, so current users aren't nagged. On first run, the panel or window opens a short guided welcome, written in her voice.
   - **The steps:**
     1. Her intro line.
     2. "What should I call you?" The answer is saved as a `user_said` fact through the existing remember path.
     3. Online brain: paste a Gemini key, optionally, with a link to get a free one.
     4. Her voice: hear the samples and pick one.
     5. How she shows up: the display mode.
     6. Her eyes: on or off, with the don't-look hotkey explained.
     7. Your agents: Claude Code connection status, and the Colab logs folder.
     8. Done.
   - **Navigation.** Every step is skippable. The welcome can be re-opened from Settings. Finishing or skipping sets `onboarded`.
2. **Health page (Settings → Health).** A live checklist, one row per thing. Each row has a status (ok, warn or off), a one-line explanation, and at most one fix button:
   - **Local brain:** llama-server is reachable, and shows its model name.
   - **Online brain:** a key is set (shown masked as `••••1a2b`), plus the time and outcome of the last test. The Test button sends one tiny request on click.
   - **Voice:** the chosen voice and whether TTS works. The Play sample button speaks one line.
   - **Mic:** whether the input device opens.
   - **Look:** whether Riya's own art pack or the placeholder is in use, and the pack path.
   - **Eyes:** enabled or not, and whether a vision test has worked. The Test button does one screen question about her own settings window only, on click, using the existing eyes path with the existing guards.
   - **Claude Code:** whether the receiver is running and port 8766 is free, whether hooks are found in `~/.claude/settings.json` (read-only check), and when the last event arrived. The Connect button runs the installer `--apply` on click, after a confirm dialog that lists exactly what will change. A Disconnect button does the same with `--remove`.
   - **Colab logs:** whether the watched folders exist.
   - **Memory:** DB size, schema version and the last backup file.
   - **Start with Windows:** autostart on or off.
3. **Key storage.**
   - The key is saved to `%LOCALAPPDATA%\Riya\secrets.env` and never written into the repo. The core reads it at start, after the repo `.env`, which still works for existing setups.
   - The key never goes to the body, logs, transcripts or memory. The body only ever sees the masked tail.
   - Replacing or removing the key applies without a restart: the online model is rebuilt.
4. **Voice picking in the UI.**
   - The core lists the feminine built-in voices, as `voice_candidates` does. Play speaks a short sample through the existing TTS path on click.
   - Choosing a voice sets `settings.voice` and takes effect on her next line.
5. **One-click actions, never automatic.**
   - Connect Claude Code, Test online, Test eyes, Play sample and Mic check each run only on an explicit click from the body, carrying a fresh nonce.
   - Nothing in v0.7 runs them automatically, on startup or from the model.
   - Claude, the builder, never runs the installer against real settings. That is still the user's click.

## 3. Non-goals and anti-goals
- **Non-goals.**
  - Generating the art: Colab stays the user's step, and the Look row only explains where the pack goes.
  - An installer or updater, or packaging into an .exe.
  - Multi-profile setups.
  - Account sign-in.
- **Anti-goals.**
  - **Key leaks.** The API key appears in the body, a log line, a transcript, a memory, an error message, git, or a test fixture, other than as the masked tail.
  - **Unasked changes.** Any outward-facing action (Claude Code settings, a network call, a screenshot) runs without the user's click.
  - **Blocking.** The welcome blocks using Riya, or nags returning users.
  - **Freezing.** A Health check hangs the UI or the core. Every check runs off the core lock, with a timeout of 5 s or less.
  - **Model-triggered actions.** A health action triggered by anything other than the body's button: the model, a tool call, or a hook.

## 4. Design

### 4.1 Core: `riya/core/health.py` (checks) and `riya/core/setup.py` (actions)
- `run_checks(ctx) -> list[HealthItem]`. `HealthItem(key, status: ok|warn|off, detail: str ≤ 120, fix: str | None)`.
  - Each check is a small function with a 5 s timeout. Checks run in a worker thread, never under the core lock.
  - They run on request: when the body opens Health, and every 30 s while the Health page is open.
- Actions are `setup.perform(action, args, nonce)`. Each one:
  - is validated against a fixed set: `online_key_set`, `online_key_clear`, `online_test`, `voice_sample`, `voice_choose`, `mic_check`, `eyes_test`, `hooks_connect`, `hooks_disconnect`, `autostart`, `onboarding_done`;
  - runs in the worker;
  - returns `{action, ok, detail}`, emitted as `setup_result`;
  - is logged to the v0.5 action log with a summary that never contains the key.
- **`hooks_connect` and `hooks_disconnect`.**
  - They call `riya.agents.install_hooks` in-process with the real paths, only from a body `setup_action` carrying the nonce of a `setup_confirm` that the body raised and the user accepted.
  - The confirm text comes from the installer's own `--print` output: which events will be added and which file will change.
  - Tests always pass temp paths.
- **Secrets.**
  - `riya/core/secrets.py` provides `load()`, `save(key)` and `clear()` on `%LOCALAPPDATA%\Riya\secrets.env`.
  - The file is written atomically, the same way as the v0.4 installer.
  - The key is validated as non-empty, at most 200 characters, with no whitespace or control characters.
  - `mask(key)` returns `"••••" + last 4`.
  - A redaction filter on the root logger scrubs the current key value from every log record.

### 4.2 Protocol
- **Core → body:**
  - `health {items}`
  - `setup_result {action, ok, detail}`
  - `setup_confirm {nonce, action, text}`, which asks the body to confirm an outward-facing action
  - `voices {items: [name], current}`
  - `settings` gains `onboarded`
- **Body → core:**
  - `health_get {}`
  - `setup_request {action, args}`, which asks for an action. For outward-facing actions, the core replies with `setup_confirm`.
  - `setup_action {nonce, yes}`. Nonces are single-use and expire after 60 s.
  - `onboarding_done {}`
- `online_key_set` sends the key from the body to the core once, over the localhost WS. The core never echoes it back.

### 4.3 Body
- **Welcome flow** (`body/welcome.html` + `src/welcome-logic.js`).
  - It opens in its own small window on first run, or from Settings.
  - Each step talks to the core through the same bridge and uses textContent only.
  - The key field is a password input. It is cleared from the DOM once sent, and never stored in the body.
- **Health section** in settings.
  - Rows show a status chip, the detail line and the fix button.
  - Outward-facing fix buttons raise the core's `setup_confirm` as a modal with the exact text, with Yes and No.
  - Refresh happens on open and every 30 s while the page is visible.
- **Main-process lists.**
  - `health` joins `FORGET_ON_DISCONNECT` and is not replayed.
  - `setup_request`, `setup_action` and `onboarding_done` are NOW_ONLY.

### 4.4 Builder-check decisions (my calls, binding)
1. **Test eyes never grabs the screen.**
   - It sends a bundled, known test image (`riya/core/assets/eyes_test.png`, generated text "Riya eye test 42") to the vision model with a fixed question. It passes if the answer contains "42".
   - This proves the vision model and key work.
   - Real glances stay governed entirely by the v0.3 policy. Her own windows are never captured, and none of the guards change.
2. **Confirm-gated vs plain-click actions.**
   - These need the `setup_confirm` → `setup_action {nonce, yes}` round trip, because they're outward-facing (another app's settings, the network, or using the key):
     - `hooks_connect`
     - `hooks_disconnect`
     - `online_test`
     - `eyes_test`
   - These are local and run directly from `setup_request` (a body click), with no nonce:
     - `online_key_set`
     - `online_key_clear`
     - `voice_sample`
     - `voice_choose`
     - `mic_check`
     - `autostart`
     - `onboarding_done`
   - Nonces exist only on the confirm path.
3. **Where the key comes from.**
   - A key in `secrets.env` overrides the repo `.env` and the process environment for `RIYA_ONLINE_API_KEY`. A key the user pastes always wins.
   - `online_key_clear` removes only the secrets.env key. If `.env` still supplies one, Health shows "set via .env (edit that file to remove it)" and Clear is disabled for that source.
   - Replacing or clearing the key rebuilds both the online and the vision model instances.
4. **Existing users skip the welcome.** `onboarded` becomes true when the DB existed before this open, meaning its `user_version` was ≥ 1 before migrating. A brand-new DB gets `onboarded=false`.
5. **Claude Code after Connect.**
   - The row's states are (settings.json decides the state; the last event only refines the wording):
     - receiver down
     - not connected: Riya's hooks are absent from settings.json, whatever the last event time (so right after
       Disconnect), with the Connect fix
     - blocked: the hooks are present but Claude Code's own settings stop them (`disableAllHooks: true`, or an
       `allowedHttpHookUrls` / `httpHookAllowedEnvVars` list without Riya's entry). A warn row, "Hooks are blocked by
       your Claude Code settings: <reason>", with no fix button: Riya never edits those keys
     - applied, restart Claude Code (hooks present, no event in the last 24 h)
     - connected (hooks present and an event in the last 24 h)
   - The blockers come from one read-only `install_hooks.blockers(settings)`. The Connect confirm text names them, and
     Connect then reports "Connected, but Claude Code will block it: <reason>" (still ok).
   - The confirm text ends with "Restart Claude Code (and open a new terminal) afterwards."
6. **The welcome's agents step is display-only.** It shows the Claude Code row and the Colab folders' status, with an "Edit in Settings" link and no folder picker.

## 5. Verification
- **Pure and unit tests:**
  - each check, using fakes (no server, server up, bad key → warn, pack missing → placeholder warn);
  - secrets save, load, clear and mask, and the log-redaction filter, where a log line containing the key comes out scrubbed;
  - nonce single-use and expiry;
  - the action allow-list.
  - The installer always runs on temp paths in tests.
- **Engine and app tests:**
  - `setup_request(hooks_connect)` → `setup_confirm`; then `setup_action yes` → the installer is called once, on the temp path; then `setup_action` with a stale or reused nonce → refused.
  - Nothing outward-facing runs without a confirm.
  - The key never appears in any emitted message, log, transcript or memory. A canary key string is scanned across all of them.
  - Checks never take the core lock.
  - Existing users get `onboarded=true` after migration.
- **Body tests:**
  - the welcome step logic;
  - the health rendering, with an HTML-sink guard;
  - the key input cleared after send;
  - the confirm modal sending the nonce.
- **Live check:** `evaluation/health_check.py` prints the Health table from a running core, read-only. Test buttons are not pressed.
